#+TITLE: Gaelan's Nix config
#+AUTHOR: Gaelan D'costa <gdcosta@gmail.com>

This is a NixOS/nix-darwin flake configuration for managing multiple systems (NixOS on x86_64-linux and macOS via nix-darwin on aarch64-darwin). It uses home-manager for user-level configuration and agenix-rekey for secrets management.

The configuration features self-contained system builders with automatic overlay composition, emacs package override management, and a clean library structure that avoids external dependencies where possible.

* Quick Start

Enter the development shell to access all tools and helper commands.
If direnv is enabled, this happens automatically on ~cd~:
#+BEGIN_SRC sh
nix develop   # or just cd into the repo with direnv active
#+END_SRC

Run ~just --list~ to see all available commands. See the
[[*Development Workflow][Development Workflow]] section for a full breakdown.

** Home-manager Fast Iteration
Home-manager changes can be applied without a full ~nixos-rebuild~ or
~darwin-rebuild~. Commands take a ~<host>~ argument:

| Command | Effect |
|---|---|
| ~just build-home <host>~ | Verify config evaluates, no activation |
| ~just inspect-home <host>~ | Build + link ~./result~ for inspection |
| ~just switch-home <host>~ | Apply; rollback via ~home-manager generations~ |

Hosts: ~arrakis~ (NixOS laptop), ~fountain-of-ahmed-iii~ (work macOS).
The ~nixos-rebuild~ / ~darwin-rebuild~ paths are unaffected.

** Emacs Fast Iteration
Emacs config lives in ~packages/emacs/init.org~. Changes fall into two
categories with different costs:

| Change | Command | Cost |
|---|---|---|
| Elisp settings, keybindings | ~just emacs-dev~ | Seconds |
| New package (new ~use-package~) | ~just emacs-dev-package~ | Minutes |
| Verify package build only | ~just build-emacs~ | Minutes |

Both ~emacs-dev~ and ~emacs-dev-package~ tangle ~init.org~ to
~$XDG_RUNTIME_DIR/emacs-dev/~ and launch an isolated emacs with
~--init-directory~, leaving ~~/.config/emacs/~ untouched. The
difference is which binary is used: ~emacs-dev~ uses the system-
installed binary (already has all packages); ~emacs-dev-package~
builds and launches from the Nix store result.

* Getting Into Nix

Nix has a reputation for poor documentation and a steep learning curve.
This section maps out what to learn, in what order, and where to find
the resources that actually helped. The goal is to save you the
flailing.

** The Nix Language First

Before anything else: Nix is a programming language. Not a config
format. A small, pure, lazy, functional language where everything
evaluates to a value and nothing has side effects. The "configuration"
you write is really just data — the Nix package manager interprets it
later.

Three things to internalise early:

1. *Attribute sets are just dictionaries.* ~{ foo = 1; bar = 2; }~ is a
   record. ~{ inherit foo; }~ is shorthand for ~{ foo = foo; }~ where
   ~foo~ is already in scope.

2. *Functions always take one argument.* ~{ a, b, c, ... }:~ is
   destructuring a single attrset argument — not three arguments. The
   ~...~ means "accept extra keys without error." ~lib.foo a b c~ is
   currying: each application returns a new function until all arguments
   are satisfied.

3. *~import~ is not magic.* ~import ./foo.nix { bar = baz; }~ loads the
   file as a function and calls it with that argument. A directory
   import loads ~default.nix~ inside it. Nothing is special — it is
   just code.

Best resources for the language:

- [[https://nixos.org/guides/nix-pills/][Nix Pills]] — the classic deep-dive, written as a series of
  experiments. Dense but worth re-reading as your understanding grows.
  Patterns like ~callPackage~, ~override~, and ~overrideAttrs~ are not
  language keywords — they are conventions that emerged organically and
  Nix Pills explains where they come from.
- [[https://nix.dev/][nix.dev]] — best-practices-oriented tutorials and reference.
  Good complement to Nix Pills.
- [[https://zero-to-nix.com/][Zero to Nix]] — gentler on-ramp from Determinate Systems, good
  if Nix Pills feels too steep at first.

** The NixOS Module System

The module system is what makes NixOS (and home-manager) composable.
Every ~.nix~ file in this repo that has ~options~ and ~config~ blocks is
a module. Understanding the split — ~options~ declares what can be set,
~config~ sets it, ~lib.mkIf~ makes it conditional — unlocks reading any
NixOS or home-manager config.

- [[https://nixos.org/manual/nixos/stable/][NixOS Manual]] — the module system chapter is the essential read.
- [[https://wiki.nixos.org/][NixOS Wiki]] — community wiki with practical examples. More
  approachable than the manual for specific topics.
- [[https://search.nixos.org/options][NixOS option search]] — indispensable for finding what options
  exist and what they do.
- [[https://search.nixos.org/packages][NixOS package search]] — find packages and their attribute names.

** Flakes

Flakes are the de-facto way most people structure Nix projects today,
though they have a controversial history — see [[https://jade.fyi/blog/flakes-arent-real/][Nix Flakes Aren't Real]]
for context on what they are and aren't. They are not necessarily the
right choice for purely Nix derivations, but they are very convenient
for personal machine/user configurations like this one: they provide
explicit dependency pinning via ~flake.lock~, a standard entry point
in ~flake.nix~, and a clean way to wire together NixOS, nix-darwin,
home-manager, and other inputs.

The key mental model: ~inputs~ are versioned dependencies (other
flakes), ~outputs~ are what this flake provides (system configs,
packages, dev shells). Everything is pinned in ~flake.lock~.

- [[https://nixos-and-flakes.thiscute.world/][NixOS and Flakes Book]] by Ryan Yin — the best single resource for
  learning NixOS + flakes + home-manager together. Book-length, clearly
  written, and kept up to date. Start here for a structured path.
- [[https://nix.dev/concepts/flakes][nix.dev flakes reference]] — concise reference once you have the
  basics.

** Home-manager

Home-manager applies the NixOS module system to user-level
configuration: dotfiles, user packages, and user services. It uses
exactly the same ~options~/~config~/~lib.mkIf~ patterns as NixOS —
once you understand one, the other follows. In this repo, reusable
modules live in ~home-manager/modules/~ and per-machine user config
lives alongside the machine config in ~machines/<host>/~.

- [[https://nix-community.github.io/home-manager/][Home-manager manual]]
- [[https://nix-community.github.io/home-manager/options.xhtml][Home-manager option reference]] — searchable list of every option.
  Keep this open while writing home-manager config.

** Overlays

Overlays are how you extend or override the nixpkgs package set. The
~final: prev:~ signature works like this:

- Use ~final~ when you are just /referencing/ a package — e.g. listing
  it as a build input or dependency. ~final~ gives you the fully
  resolved package set, so you get any version that other overlays may
  have modified.
- Use ~prev~ when you are /deriving something from/ a package — e.g.
  calling ~overrideAttrs~ to modify it. You need the concrete base
  implementation to build on, and using ~final~ here risks an infinite
  loop if the package is defined in terms of itself.

This repo uses overlays to bring in ~emacs-overlay~ packages and
override the ones it breaks.

- [[https://wiki.nixos.org/wiki/Overlays][NixOS Wiki: Overlays]] — practical intro with examples
- [[https://nixos.org/manual/nixpkgs/stable/#chap-overlays][nixpkgs manual: Overlays]] — the authoritative reference

These are the tools layered together here, each with its own docs:

- [[https://github.com/nix-community/home-manager][home-manager]] — user-level config management
- [[https://github.com/nix-community/emacs-overlay][emacs-overlay]] — latest Emacs builds and MELPA/ELPA packages via Nix
- [[https://github.com/ryantm/agenix][agenix]] — age-encrypted secrets for NixOS
- [[https://github.com/oddlama/agenix-rekey][agenix-rekey]] — extends agenix with per-host rekeying and YubiKey
  support
- [[https://github.com/NixOS/nixos-hardware][nixos-hardware]] — community hardware configuration modules (this
  repo uses the Framework 13 AMD module)
- [[https://github.com/hraban/mac-app-util][mac-app-util]] — makes Nix-installed macOS apps visible to Spotlight
  and the Dock. Nix installs apps into the store under
  ~/nix/store/...~, which Spotlight does not index. mac-app-util
  creates a small wrapper ~.app~ bundle (a "trampoline" — an
  intermediate that immediately redirects to the real target) in
  ~~/Applications/~ for each installed app. Spotlight indexes
  ~~/Applications/~, so the trampoline makes the app discoverable
  without Spotlight needing to know about the Nix store.

** This Repo's Patterns

/~scanPaths~/ (~lib/scanPaths.nix~): automatically imports every ~.nix~
file and subdirectory from a path. Used in ~home-manager/modules/~ so
new modules are picked up without being added to an imports list
manually.

/System builders/ (~lib/nixosSystem.nix~, ~lib/darwinSystem.nix~):
wrap ~nixpkgs.lib.nixosSystem~ / ~darwin.lib.darwinSystem~ to handle
overlay composition, home-manager wiring, and ~specialArgs~ in one
place. Each machine config just calls the builder with its modules.

/~@args~ forwarding/: ~lib/default.nix~ accepts its arguments as
~{ lib, nixpkgs, ... }@args~ and passes ~args~ wholesale to the system
builders. Each builder extracts only what it declares. This avoids
threading every argument manually through the call chain.

/~inputs.nixpkgs.follows~/ convention: every flake input that itself
depends on nixpkgs should declare ~inputs.nixpkgs.follows = "nixpkgs"~
(see ~flake.nix~). Without this, each input brings its own pinned
nixpkgs into the closure — multiple versions get downloaded, evaluated,
and potentially built. Pinning all inputs to the same nixpkgs keeps the
dependency graph consistent and avoids redundant work. There are two
exceptions: ~nixpkgs-unstable~, which is intentionally a different
channel, and ~nix-darwin~, which does /not/ follow the flake's main
~nixpkgs~. The ~nix-darwin~ input implicitly pins its own nixpkgs to a
branch that has validated testing on macOS, so overriding it with
~follows~ could pull in a nixpkgs revision that hasn't passed Darwin
CI.
